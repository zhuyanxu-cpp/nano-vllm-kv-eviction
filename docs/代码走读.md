# 代码走读：一次 KV 驱逐是怎么发生的

> **用途**：你已经读过论文、也写过这些代码，但一周不看就会忘。这份文档按**真实执行顺序**走一遍，每个节点给「文件:行 / 在做什么 / 不变量 / 这里最容易错的地方」。
>
> **先记住这条链**（背下来，面试被问"讲一下你的实现"就照这个顺序说）：
>
> ```
> Scheduler.schedule()          decode 分支，can_append 失败
>   └─ _evict_for_blocks(1)     开关检查 + 选中受害者
>       └─ _pick_victim()       谁让得出最多 KV
>       └─ Scheduler.evict()    ── 从这里开始是"一次驱逐"的正文
>           ├─ planned_drop()   → plan_drop()          丢多少（块算术）
>           ├─ score_provider() → read_eviction_scores 读重要性分数（h2o）
>           ├─ select_keep_indices()                   丢哪些（策略）
>           ├─ plan_eviction()  → EvictionPlan          出计划（可拒绝）
>           ├─ move_slots()     → GPU 就地压缩         唯一的副作用
>           ├─ commit_eviction()                       提交块表与计数器
>           └─ _release_block_scores()                 清掉被释放块的分数
>   └─ continue → can_append 再判一次 → may_append 分配腾出来的块
> ```
>
> **释放路径上还有两个入口也调 `_release_block_scores`**：`preempt()`（KV 整条丢弃）和序列 FINISHED（正常结束）。见 §10。
>
> 全部行号基于当前工作副本，可用 `grep -n` 现场复查。

## 0. 前置状态：一次驱逐发生时，引擎里有什么

先把"现场"写清楚，否则后面每一步都缺上下文。

| 对象 | 状态 | 出处 |
| --- | --- | --- |
| KV 池 | 一块连续大张量 `(2, 28层, 48块, 256token, 8头, 128维)`，48 块 = 12288 token | `model_runner.py:120` |
| 当前序列 | 状态 `RUNNING`（= prefill 已完成），`block_table` 里是它占的物理块 id | `scheduler.py:81-84` |
| 逻辑长度 | `num_tokens`（含已经 append、但 KV 还没写的那个 token） | `sequence.py:23` |
| 物理长度 | `physical_num_tokens = num_tokens − num_evicted_tokens` | `sequence.py:72-75` |
| 驻留长度 | `resident_num_tokens = min(physical, len(block_table) × 256)` | `sequence.py:77-88` |
| 分数 buffer | `float32[48×256]`，按物理槽位索引，只在 `policy == "h2o"` 时分配 | `model_runner.py:125-127` |
| 释放块的分数清理 | 任何块回到自由链时，它的 256 个槽位必须归零，否则下一个占用者会继承旧分数 | `model_runner.py:148-163`、`scheduler.py:115 / 218 / 245` |

**为什么 `resident` 会不等于 `physical`（一句话）**：`append_token` 立刻把 `num_tokens` 加一，但新 token 的块要等下次调度时 `may_append` 才分配。所以**每个块边界上恰好有一步**，`resident = physical − 1`。驱逐必须能用 `resident`，因为内存压力正好出现在这一步（`sequence.py:81-86` 的注释就是为这件事写的）。

## 1. `can_append` 失败：驱逐的触发点

**位置**：`nanovllm/engine/scheduler.py:90-108`、`nanovllm/engine/block_manager.py:130-143`

```python
# scheduler.py:90-100
while self.running and len(scheduled_seqs) < self.max_num_seqs:
    seq = self.running.popleft()
    while not self.block_manager.can_append(seq):
        if self._evict_for_blocks(1, {s.seq_id for s in scheduled_seqs}):
            continue
        if self.running: self.preempt(self.running.pop())
        else:            self.preempt(seq); break
    else:
        seq.num_scheduled_tokens = 1
```

**在做什么**：取出一个 RUNNING 序列准备走一步 decode。`can_append` 问"下一步那个 token 需要新块吗，自由块够吗"：

```python
# block_manager.py:130-143
def needs_new_block(self, seq):
    return (seq.physical_num_tokens - 1) // self.block_size >= len(seq.block_table)
def can_append(self, seq):
    return len(self.free_block_ids) >= self.needs_new_block(seq)
```

**不变量**：`needs_new_block` 完全由**块表**推导，输入是 `physical_num_tokens`（不是 `num_tokens`）。

**这里最容易错的地方（三个）**
1. **用 `num_tokens` 而不是 `physical_num_tokens`**：驱逐之后逻辑长度带上了被丢掉的 token，`(num_tokens−1)//256` 会比实际需要的块号大，于是提前分块 → 块表出现空余容量 → `len(block_table) == ceil(physical/256)` 这个恒等式破掉，后面所有算术都不可信。这正是上游 `len(seq) % block_size == 1` 的失效方式（`docs/bench_results.md` §4 最后一行）。
2. **把 `(physical−1)//256 >= len(table)` 写成 `>`**：差一，会在恰好需要新块的那一步漏分块；`slot_mapping` 随后落到块表外（`model_runner.py:261`），写进别人的槽位。
3. **忘记 `can_append` 是"够不够"的布尔值，不是"要不要"**：`len(free) >= needs_new_block`——`needs_new_block` 返回 bool，`True == 1`，所以语义是"需要 1 块时有 1 块就行"。改动这里必须同时看 `may_append`（`145-147`）真的去分配。

## 2. `_evict_for_blocks`：开关 + 入口

**位置**：`scheduler.py:176-183`

```python
def _evict_for_blocks(self, blocks_needed=1, exclude_ids=frozenset()) -> bool:
    if not self.kv_eviction:                       # 178-179
        return False
    victim = self._pick_victim(blocks_needed, exclude_ids)   # 180
    if victim is None:
        return False
    return self.evict(victim, blocks_needed)       # 183
```

**在做什么**：三段式——功能开关 → 选受害者 → 执行。返回 `True` 表示"确实释放了至少一块"，调用者据此决定 `continue`（重判 `can_append`）还是走 `preempt`。

**不变量**：**只有返回 True 才会重试**，所以 `evict()` 的返回值必须是"真的释放了块"而不是"我尝试过了"——这一点由 `evict` 最后一行保证（`scheduler.py:231`：`return len(plan.freed_block_ids) > 0`）。

**这里最容易错的地方**
1. **`blocks_needed` 的真实含义**：在 decode 分支传的是常量 `1`（`scheduler.py:94`）；只有准入分支才传 `shortfall`（`65-68`）。别把它当成"要释放的块数"的精确目标——`plan_eviction` 可能一次释放多块（`p_adm.json` 里 26 次事件释放了 40 块）。
2. **`exclude_ids` 是"正在这个 batch 里"的序列**：decode 分支传 `{s.seq_id for s in scheduled_seqs}`（`94`）——当前序列已经 `popleft` 出去了，所以它也在里面。漏了这个过滤，就会去动"这一步正要用的 KV"。
3. **`frozenset()` 作为默认参数是安全的**（不可变），但别改成 `set()`——可变默认参数会跨调用共享。

## 3. `_pick_victim`：谁当受害者

**位置**：`scheduler.py:158-174`

```python
victim, most = None, 0
for seq in self.running:
    if seq.seq_id in exclude_ids: continue                    # 162-166
    if seq.status is not SequenceStatus.RUNNING or not seq.block_table: continue  # 167-168
    if self.planned_drop(seq, blocks_needed) <= 0: continue   # 169-170
    headroom = self.evictable_tokens(seq)                     # 171
    if headroom > most: victim, most = seq, headroom          # 172-173
```

**在做什么**：在 `running` 里找"可让出 KV 最多"的序列。

**不变量（两条）**
- 受害者必须**能真的丢出东西**：`planned_drop > 0`（169）——这个检查和后面的执行用的是**同一个函数**，所以不会出现"选中了却丢不动"。
- 受害者必须**已经 prefill 完成**：`status is RUNNING`（`150`、`167`）。这是整个设计里最关键的一条正确性前提，理由见 §7 的"为什么只能驱逐 decode 序列"。

**这里最容易错的地方**
1. **`evictable_tokens` 用 `resident_num_tokens` 而不是 `num_tokens`**：`max(0, resident − retention_floor)`（`scheduler.py:152`）。用 `num_tokens` 会把已经丢掉的 token 再算一次，headroom 偏大。
2. **`status is RUNNING` 不能用 `is_prefill` 代替**：`is_prefill` 在 preempt 时被设回 True（`112`），在 decode 时设 False（`103`），但**它描述的是"这一步跑的是什么"**，而 `status` 描述的是"这条序列的生命周期位置"。用错会在 chunked prefill 中途的序列上开刀。
3. **`len(seq.block_table) == 0` 也要排除**（`167`）：Wait 状态刚被 allocate 之前的序列块表为空（`allocate` 里才 append，`block_manager.py:102-119`），对空块表算物理索引会直接崩。
4. **选择准则是"headroom 最大"而不是"最不重要的"**：这是**调度视角**的选择（谁的 KV 最多，丢它一块最省事），策略（丢哪些）在下一层才介入。别把两层混起来讲。

## 4. `planned_drop` → `plan_drop`：丢多少

**位置**：`scheduler.py:154-156` → `kv_eviction.py:116-138`

```python
def planned_drop(self, seq, blocks_needed):
    return plan_drop(seq.physical_num_tokens, len(seq.block_table), blocks_needed,
                     self.block_size, self.retention_floor(seq))

# kv_eviction.py:135-138
drop = physical - (table_blocks - blocks_needed) * block_size
if drop <= 0: return 0
return int(min(drop, max(0, physical - min_keep)))
```

**在做什么**：算出"要丢多少个 token 才能真正少占 `blocks_needed` 个块"，再用保留下限夹一下。

**不变量**
- 结果要么 0（不可行），要么**保证驱逐后至少空出一个块**。
- 驱逐后的物理长度 `>= min_keep`，`min_keep = max(sink+window, ceil(prompt × ratio))`（`scheduler.py:130-133`、`kv_eviction.py:113`）。

**这里最容易错的地方（这一节是全书最容易翻车的）**
1. **分母用块表块数，不是 `ceil(physical/256)`**：这两个数在正常情况下相等，但在"刚 append、块还没分配"的那一步**必须**用块表（`len(seq.block_table)`）。用 `ceil` 会多算一块，于是丢掉一部分本来不用丢的 KV。
2. **`physical` 里必须包含那个"已 append 但没有 KV"的 token**：注释 `128-133` 明写了——不算它会差 1 个 token，clamp 会把**可行**的驱逐判成不可行（表现为"压力很大却一直不驱逐、直接抢占"）。
3. **clamp 是 `min(drop, ...)` 而不是 `max(...)`**：这里曾经写成"至少丢到 retention budget"，一次 1 块的请求因此丢了约 510 个 token（本来 257 就够）。**注意口径**：`docs/bench_results.md` §4 记的"18.8s → 28.7s"那次**同时开着准入驱逐**，两个因素没有分离，所以那 53% 不能单独归给 clamp；能站住的只有定性结论——**丢 510 个而 257 个就够，严格更差**。`min` 是"丢够就好"，`max` 是"丢到某个目标"，后者会为了达标而丢掉没人要求丢的上下文。
4. **`drop <= 0` 时返回 0 而不是负数**：调用方统一用 `> 0` 判断可行性（`169`、`189`）。

## 5. `Scheduler.evict`：一次驱逐的编排

**位置**：`scheduler.py:185-231`。这是全文的"主干"，先看全局再看分支：

```python
num_resident = seq.resident_num_tokens                      # 187
drop = self.planned_drop(seq, blocks_needed)                # 188
if drop <= 0: return False                                  # 189-190

scores = None
if self.eviction_policy == "h2o":                           # 192-199
    slots = [self.block_manager.slot_of(seq, i) for i in range(num_resident)]
    scores = self.score_provider(slots)

keep = select_keep_indices(policy, num_resident, sink, window, drop, scores, seed=seq.seq_id)  # 201-206
plan = self.block_manager.plan_eviction(seq, keep)          # 208-210
if plan is None: return False

if self.kv_cache_io is not None:
    self.kv_cache_io.move_slots(plan.src_slots, plan.dst_slots)   # 212-215

self.block_manager.commit_eviction(seq, plan)               # 217
self._release_block_scores(plan.freed_block_ids)            # 218 ← 清掉刚释放块的分数
self.stats.events += 1; ...                                 # 219-221
return len(plan.freed_block_ids) > 0                        # 231
```

**不变量（顺序即不变量）**
1. **先算分再选，先出计划再动手，先搬完再提交，最后清分数**——五段严格有序，任何一段失败都不留半改状态。
2. `scores` 与 `keep` 都以**物理索引**为坐标系（`0..num_resident−1`），不是逻辑 token 位置。
3. `move_slots` 是**唯一**的 GPU 副作用；`commit_eviction` 是**唯一**改块表和计数器的语句。
4. **块一旦离开这条序列，它的分数必须在同一次调用里被清掉**（`218`）——因为 `commit_eviction` 刚把 `freed_block_ids` 还回自由链，别的序列随时可能拿到它们。

**这里最容易错的地方**
1. **`num_resident` 而不是 `physical_num_tokens`**（`187`）：`select_keep_indices` 会断言 `scores.shape[0] == num_resident`（`kv_eviction.py:91`），用错长度会直接 assert fail，或者更糟——把"还没分配块的那个 token"算进去，`slot_of(seq, num_resident)` 索引到块表外。
2. **`seed=seq.seq_id`**（`204`）而不是固定 seed：random 策略对同一条序列在多次驱逐中保持一致的可复现性，同时不同序列不共用随机流。用 `0` 会让所有序列的相关性人为提高。
3. **`plan is None` 的三个原因不在这一层**（见 §7），这里只是"计划失败就当没发生"——注意此时**分已经读了**（白读一次），这是可接受的浪费，但别在 `plan_eviction` 之后再去读分。
4. **`if self.kv_cache_io is not None`**（`213`）：这是为了让 CPU 单测能跑（测试注入 `FakeKvCacheIO`，`tests/test_eviction_scheduler.py:27-40`）。生产路径永远非空。把这段当成"可选功能"是误读——它是**可测性**设计。
5. **统计在提交之后**（`219-221`）：顺序反了的话，一次失败的驱逐也会进统计，`tokens_evicted` 就再也对不上 `results/*.json` 了。
6. **`_release_block_scores` 必须在 `commit_eviction` 之后**（`217` → `218`）：反过来的话，`plan.freed_block_ids` 对应的块可能已经被别的序列拿走并开始累积分数，你这一清就把**新主人**的分数抹掉了。顺序反了不会崩，只会让 H2O 少算一部分质量——又是一种"静默变差"。

## 6. `select_keep_indices`：丢哪些

**位置**：`kv_eviction.py:41-96`

```python
head_end   = min(sink, num_resident)                 # 70
tail_start = max(head_end, num_resident - window)    # 71
head   = arange(0, head_end)                         # 72
tail   = arange(tail_start, num_resident)            # 73
middle = arange(head_end, tail_start)                # 74
drop_count = min(max(drop_count, 0), len(middle))    # 76
...
lru:    chosen = middle[-keep_middle:]               # 82-83
random: chosen = np.sort(rng.choice(...))            # 84-86
h2o:    order = np.lexsort((middle, s[middle]))[::-1]  # 87-94
return np.concatenate([head, chosen, tail])          # 96
```

**在做什么**：把驻留 token 切成 sink / middle / window 三段，只在 middle 里按策略删 `drop_count` 个，返回**升序**的存活物理索引。

**不变量**
1. **`head` 和 `tail` 永不参与丢弃**（StreamingLLM 的 sink 和 recency 假设）。
2. 返回值**严格升序**（`lru` 天然升序；`random` 显式 `np.sort`；`h2o` 显式 `np.sort`；拼接顺序也是升序）。
3. 长度 = `num_resident − drop_count`。

**这里最容易错的地方**
1. **h2o 的 `lexsort` 方向**：`np.lexsort((middle, s[middle]))[::-1]`——主键是 `s`（分数），次键是 `middle`（索引）。`[::-1]` 让分数**降序**，同时让**同分时索引大的（更新的）排在前面**。写反会让 tie 全部偏向最老的 key，H2O 就退化成 LRU 的劣化版。这是"看起来对、结果悄悄变差"的典型。
2. **排序必须保持升序**：`plan_eviction` 的 `dst` 是按 `j = 0..num_keep−1` 递增生成的（`block_manager.py:222-223`），如果 `keep_indices` 不是升序，`src`/`dst` 的对应关系还在（一一对应），但**物理索引语义**就乱了——更致命的是"存活者密度"这个不变量会被破坏，后面 `context_lens = physical_num_tokens` 就不再成立。
3. **`drop_count` 的 clamp 在函数内部（`76`）而不在调用方**：因为 middle 的长度依赖 sink/window 的裁剪，调用方算不出来。
4. **`keep_middle <= 0` 时返回空（`78-79`）**：这时返回值只有 head+tail，`plan_eviction` 的 `new_num_blocks` 可能等于旧值 → 返回 None → 白跑一次。这是设计接受的行为，不是 bug。
5. **`num_resident` 被强制转 int（`69`）**：上游调用传进来的可能是 numpy 整数，`np.arange` 混用会得到奇怪 dtype。

## 7. `BlockManager.plan_eviction`：出计划（也是三个拒绝点）

**位置**：`block_manager.py:191-232`

```python
expected_blocks = (seq.resident_num_tokens + self.block_size - 1) // self.block_size
assert len(seq.block_table) == expected_blocks, (...)         # 204-205
num_keep = len(keep_indices)
if num_keep == 0 or num_keep >= seq.resident_num_tokens: return None   # 207-208
if any(self.blocks[b].ref_count > 1 for b in seq.block_table): return None  # 209-210
num_evicted = seq.resident_num_tokens - num_keep              # 214
physical_after = seq.physical_num_tokens - num_evicted        # 215
new_num_blocks = (physical_after + self.block_size - 1) // self.block_size  # 216
if new_num_blocks >= len(seq.block_table): return None        # 217-218

old_table = list(seq.block_table)
src = [self.slot_of(seq, int(i)) for i in keep_indices]        # 221
dst = [old_table[j // bs] * bs + j % bs for j in range(num_keep)]  # 222-223
return EvictionPlan(src, dst, old_table[new_num_blocks:], num_keep, num_evicted,
                    len(old_table), new_num_blocks)           # 224-232
```

**在做什么**：把"保留哪些"翻译成"哪些槽位搬到哪些槽位"，同时算清要释放哪些块。**这一层不做任何副作用**。

**三个拒绝点（背下来，被问"什么情况下不驱逐"就答这三条）**
1. `num_keep == 0 or num_keep >= resident`（`207-208`）：没得丢，或者丢了等于没丢。
2. **任何块 `ref_count > 1`**（`209-210`）：共享前缀块，就地重写会污染其他读者。**这是"共享前缀不支持"的唯一实现位置。**
3. `new_num_blocks >= len(block_table)`（`217-218`）：腾不出整块，做了也白做。

**不变量**
- **`src` 与 `dst` 等长且一一对应**（`221-223`），`dst` 严格递增且从 0 开始密集。
- **`freed_block_ids = old_table[new_num_blocks:]`**（`227`）：被释放的永远是块表**尾部**的块——这正是"存活者从槽 0 密集排列"的必然结果。
- 断言 `204-205` 是**整个设计的地基**：`len(block_table) == ceil(resident/256)`。它一旦不成立，`slot_of` 和 `needs_new_block` 全都不可信。

**这里最容易错的地方**
1. **断言用 `resident` 而不是 `physical`**（`204`）：边界那一步两者差 1，用 `physical` 会在**最需要驱逐的时刻**断言失败（内存压力恰好出现在块边界）。
2. **`num_evicted` 用 `resident − num_keep`，但 `physical_after` 用 `physical − num_evicted`**（`214-215`）：那个"已 append 但没有 KV"的 token **既没有被驱逐也不能被丢**，它永远留在物理长度里。这两个式子看起来不对称，是对的。
3. **`dst` 里的 `old_table[j // bs]`**（`222`）：用的是**旧块表**——因为搬完之后这些块仍然被这条序列持有（释放的是尾部）。写成 `seq.block_table[:new_num_blocks]` 会一样，但语义上"目标槽位在现有块内"更清楚。
4. **`new_num_blocks >= len(...)` 用 `>=`**：等于时说明腾不出块，必须拒绝；写成 `>` 会放行一次"零收益"的驱逐，白搬 KV。
5. **不要在 `plan_eviction` 里改任何状态**：它被 `_pick_victim` 之外的路径间接调用（`_evict_for_blocks` → `evict`），必须保证"计划失败 = 什么都没发生"。

## 8. `ModelRunner.move_slots`：GPU 上就地压缩

**位置**：`model_runner.py:165-196`

```python
src = torch.tensor(src_slots, dtype=torch.long, device="cuda")
dst = torch.tensor(dst_slots, dtype=torch.long, device="cuda")
if self.config.eviction_bulk_kv_move:                 # 180-188  故意保留的旧实现
    shape = self.kv_cache.shape
    kv = self.kv_cache.view(2, shape[1], -1, shape[-2], shape[-1])
    kv[:, :, dst] = kv[:, :, src]
    ...
    return
num_layers = self.kv_cache.shape[1]
for layer in range(num_layers):                       # 191
    for kv in range(2):                               # 192
        block = self.kv_cache[kv, layer].view(-1, num_kv_heads, head_dim)
        block[dst] = block[src]                       # 194：advanced indexing 自带拷贝，不需要 clone
if self.eviction_scores is not None:
    self.eviction_scores[dst] = self.eviction_scores[src]   # 195-196
```

**在做什么**：K 和 V 各自逐层做 `dst ← src`（默认路径），加上分数 buffer 一起搬。`eviction_bulk_kv_move=True` 时走 180-188 那条一次性的老路——**它存在只是为了复现下面那个负结果**。

**不变量**
- **`src`/`dst` 都是物理槽位**（不是块 id，不是 token 位置）。
- **`dst` 必须互不重复**（`src` 同理）：`block[dst] = block[src]` 是 gather-then-scatter，PyTorch 的 advanced indexing 会先取值再写，所以 `src`/`dst` 有重叠是安全的；但 `dst` 重复会导致结果不确定。
- 分数 buffer 必须跟着搬，否则"哪个 key 重要"会张冠李戴（因为 buffer 按**槽位**索引）。

**这里最容易错的地方**
1. **不要"优化"成 `kv[:, :, dst] = kv[:, :, src]`**：一次申请约 1GB 临时张量，4GB 卡上 allocator 抖动，**后面的 decode step 全部变慢**。同一负载（16×1024）实测：`p_adm_bulk.json` decode **12.33s** vs `p_adm.json`（逐层）**8.81s = +40%**，wall 25.94s vs 22.42s。
2. **CPU 侧计时会骗你**：bulk 版本的 `move_seconds` 是 **0.022s**，逐层版本是 **0.159s**——大张量搬在 CPU 计时里看起来便宜 7 倍，实际却让 decode 慢 40%。CUDA 是异步的，CPU 只量到 launch。
3. **不要加 `.clone()`**：注释 `194` 说的就是这件事，advanced indexing 已经产生新张量。
4. **`view(-1, num_kv_heads, head_dim)` 依赖 KV 池是连续的**（`120` 用 `torch.empty` 分配，`[kv, layer]` 切片连续）。如果有人改成非连续布局，`.view` 会抛错——那时得换 `.reshape` 并接受一次拷贝。
5. **搬移与模型执行必须错开**：这段是在调度步之间调的（`scheduler.py:212-215`），此时没有 kernel 在读这些槽位。如果哪天把驱逐挪进 forward 里，就会出现读写竞争。
6. **`block[dst] = block[src]` 在 `inference_mode` 下的行为**：整个 run 在 `@torch.inference_mode()` 下（`model_runner.py:275`），对 inference tensor 做原地写是允许的；但别在别处对这种张量求梯度。

## 9. `BlockManager.commit_eviction`：提交

**位置**：`block_manager.py:234-247`

```python
for block_id in seq.block_table:
    self._deregister_hash(block_id)                  # 236-237
for block_id in plan.freed_block_ids:
    block = self.blocks[block_id]
    block.ref_count = 0                              # 244
    self._deallocate_block(block_id)                 # 245
seq.block_table = seq.block_table[:plan.new_num_blocks]   # 246
seq.num_evicted_tokens += plan.num_evicted           # 247
```

**在做什么**：把该序列**所有块**从内容哈希索引里摘掉，释放尾部块，截断块表，累加驱逐计数。

**不变量**
1. **`len(block_table) == ceil(physical/256)`** 在 246 行之后重新成立。
2. **被驱逐的序列永久退出前缀缓存**：`hash_blocks` 里 `if seq.has_evicted_kv: return`（`156-157`），所以之后再也不会有块被登记。
3. **释放的块 `ref_count = 0` 后回自由链**，不是 `reset()`。

**这里最容易错的地方（两条，都是踩过的）**
1. **必须调 `_deregister_hash`，不能只 `block.hash = -1`**（`176-189` 的注释）：`_allocate_block` 的清理条件是 `block.hash != -1 and hash_to_block_id.get(block.hash) == block_id`（`65-66`）——先置 -1 就再也不满足它，字典条目永久残留；随后 `can_allocate` 命中它，拿 `block.token_ids` 和 `seq.block(i)` 比对（`89`），**两边都是元数据**，永远相等，于是把 KV 已被改写的块当合法前缀发出去。
2. **释放块要用 `ref_count = 0` 而不是 `block.reset()`**（`240-243` 注释）：`reset()` 会把 `ref_count` 设成 1，那是"已经交给新主人"的语义；这样回自由链，下一次 `_allocate_block` 会在 `assert block.ref_count == 0`（`64`）上炸。
3. **摘哈希要对 `seq.block_table` 全表做**（`236-237`），不只是被释放的尾部块：**保留下来的块内容也变了**（它们现在装的是别的 token 的 KV），哈希索引同样失真。
4. **`num_evicted_tokens += plan.num_evicted` 用累加**：多次驱逐要累加，赋值会丢掉历史（而 `physical = num_tokens − num_evicted` 全靠它）。

**紧接着还有一步**：`evict` 在 `commit_eviction` 之后立刻调 `self._release_block_scores(plan.freed_block_ids)`（`scheduler.py:218`）——块已经回到自由链，它的分数必须同时清零。见 §10。

## 10. `_release_block_scores`：块回到自由链时清掉它的分数（修复项）

**位置**：`scheduler.py:122-126`（统一入口）→ `model_runner.py:148-163`（真正干活）

```python
# scheduler.py:122-126
def _release_block_scores(self, block_ids: list[int]):
    """Drop stale importance scores when blocks go back to the free pool."""
    clear = getattr(self.kv_cache_io, "clear_block_scores", None) if self.kv_cache_io else None
    if clear is not None and block_ids:
        clear(block_ids)

# model_runner.py:158-163
if self.eviction_scores is None or not block_ids:
    return
blocks = torch.tensor(block_ids, dtype=torch.long, device="cuda")
slots = (blocks[:, None] * self.block_size
         + torch.arange(self.block_size, device="cuda")[None, :]).reshape(-1)
self.eviction_scores[slots] = 0
```

**为什么需要它**：分数 buffer 按**物理槽位**索引，而槽位比序列活得久。块被释放、再分配给新序列之后，如果不清理，新序列会在那些槽位上**继承上一个占用者的累计注意力质量**，于是 H2O 的"保留 heavy hitter"判断建立在别人的历史上——**能跑通，但策略会悄悄偏掉**。

**三个调用点（缺一不可）**
1. `preempt()`（`scheduler.py:113-115`）：先把块表拷出来，`deallocate` 之后再清——因为 `deallocate` 会 `seq.block_table.clear()`（`block_manager.py:128`）。
2. 驱逐释放尾块（`scheduler.py:218`）：紧接着 `commit_eviction`。
3. 序列 FINISHED（`scheduler.py:243-245`）：和 `deallocate` 同一段，顺序同样是先拷块表。

**不变量**：**任何把块还回自由链的路径，都必须在同一处清分数。**新增释放路径时漏掉一个，就是一个静默的策略偏差——不会有报错，只会让选择变差。

**这里最容易错的地方**
1. **`preempt` / FINISHED 必须先把 `block_table` 拷出来**（`113`、`243`）：`deallocate` 里有 `seq.block_table.clear()`，之后再读就是空的——清分会静默不执行。
2. **别以为 `getattr(..., None)` 是"给生产路径省一次调用"**（`124`）：它是为了让 `FakeKvCacheIO` 这类只实现部分方法的测试替身也能工作。生产路径的 `kv_cache_io` 就是 `ModelRunner`，永远有这个方法。
3. **清的是整块 256 个槽位，不是"还活着的那些"**（`161-162`）：块的语义单位就是 256 个槽位，逐个区分没有意义。
4. **它不是 correctness 修复，别讲错**：分数不参与任何地址计算，所以清不清都不影响 KV 的正确性；它修的是**选择质量**。这也是为什么它只值一个单测，而不是一条端到端的精度结论（H2O 22/24 → 23/24 只是 1 个命中，噪声）。
5. **对应测试**：`tests/test_eviction_scheduler.py:148-159`（断言 `FakeKvCacheIO.cleared` 非空，且驱逐确实发生过）。

## 12. 下一步 decode：两条路彻底分道

**位置**：`model_runner.py:247-268`

```python
positions.append(len(seq) - 1)                                    # 257  逻辑
context_lens.append(seq.physical_num_tokens)                      # 260  物理
slot_mapping.append(seq.block_table[-1] * self.block_size
                    + seq.physical_last_block_num_tokens - 1)     # 261  物理
```

**为什么这样是对的（背下来，这是最常被追问的一点）**
- 缓存里的 **k 在写入时就带上了当时的 RoPE 相位**：`qwen3.py:85` 先 `rotary_emb(positions, q, k)`，`attention.py:94` 才 `store_kvcache`。驱逐只搬槽位、不改数值。
- 新 query 用**真实逻辑位置**旋转，于是 `q·k` 只依赖相位差——**相对位置完全正确**。
- `context_lens` 是"这一步要 attend 多少个 key"，存活者密集排在槽 0..physical−1，所以这个数正好是 key 的个数（`flash_attn_with_kvcache` 的 `cache_seqlens`，`attention.py:104`）。

**容易错的地方**：把 `positions` 也改成物理（`physical − 1`）→ 相位差全错 → 输出直接乱码；把 `context_lens` 用逻辑 → 会读到块表外的槽位（因为 `block_tables` 只按实际块数填）。

## 13. `postprocess` / `hash_blocks`：把驱逐过的序列挡在前缀缓存外

**位置**：`scheduler.py:233-246`、`block_manager.py:149-167`

```python

```

```python

```

**不变量**：`hash_blocks` 必须在 `num_cached_tokens` 更新**之前**调用（它用 `num_cached_tokens` 和 `num_scheduled_tokens` 算要登记的块区间，`158-159`）。

**容易错的地方**
1. **`num_cached_tokens == num_tokens` 永远不成立**：`num_cached_tokens` 先加（`236`），`append_token` 后加（`240`），所以 decode 期间恒定差 1。要判"prefill 完成"用 `status`（`81-84` 设置 RUNNING），不要用这个等式。
2. **`hash_blocks` 的位置**：放到 `append_token` 之后，区间会多算一块。
3. **`has_evicted_kv` 是"永久"的**：只有 `preempt` 会重置它（`scheduler.py:118` → `sequence.py:105-107`），因为那时整条序列的 KV 都不要了、准备从头重算。
4. **序列结束时别忘了清分数**：这一段的 FINISHED 分支里 `deallocate` 之后紧跟 `_release_block_scores`（`243-245`），漏掉就是 §10 说的静默偏差。

## 17. 如果你要动这套代码：先读这五处

1. `sequence.py:64-107`（逻辑/物理的全部定义）——**改这里等于改所有地址**。
2. `block_manager.py:130-147` + `191-232`（块表恒等式与计划）——**断言的来源**。
3. `block_manager.py:149-189`（前缀缓存的进入与退出）——**静默错误的高发区**。
4. `model_runner.py:247-268`（哪条路用哪个长度）——**唯一会同时碰到两个坐标系的地方**。
5. `scheduler.py:110-126` + `model_runner.py:148-163`（释放路径与分数清理）——**三个调用点，漏一个就静默变差**。

只要这几处的不变量成立，中间的调度、策略、搬运都是可以替换的实现细节。
